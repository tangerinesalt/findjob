# findjob 下一步改造指南：检索覆盖、线索续接与核实闭环

日期：2026-10-09。基线：当前项目及已安装的 findjob 0.2.2。

本文是待实施指南，不代表改造已完成。目标是修复真实任务中已经出现的执行遗漏，使额外平台额度带来补充机会，同时维持常规跨平台检索能力。优先改善技能指令和交接，再增加必要的轻量校验；沿用本次不走 superpowers 工作流程的约定。

## 1. 已证实的问题与证据边界

| 问题 | 本次证据 | 应当修复的环节 |
|---|---|---|
| 额外额度实际变成平台上限 | 两个平台分支各只分到额外5次，完成后没有安排常规池接续；技能原文允许常规池继续查询它们 | 任务分配、主代理接管 |
| 常规检索过早结束 | 10月8日59次查询、54次发现；10月9日31次查询、26次发现，常规池仍剩39次 | 分批调度、全局停止判断 |
| 既有有效线索没有进入新任务 | 百变互动高级岗、易弧相邻岗、布勒官网岗均未复核；同日联网验证已经纳入的轩宇也没有进入真实任务 | 开始阶段的线索继承 |
| 待核实岗位缺少公开反查 | 北大医学部列名岗位存在实际雇主疑点；北斗天地正文失败。两条均未进一步查询原发布平台、官网或其他公开同岗来源 | 核心证据补查 |
| 同类日期差异处理不一致 | 百变中级岗两版日期均在窗口内却转待核实；上一轮步速者同类差异保留并说明 | 证据裁决、冲突归类 |
| 局部验证被用于评价整体效果 | 同批22条非LinkedIn事实判定一致，只能验证这些输入的规则隔离，无法发现未进入输入的岗位 | 验收口径、交付说明 |

补充核对发现，同日联网验证中的广东智动未来岗位也没有进入真实任务的候选或访问记录。下一轮应统一核对相关历史结果，避免依赖用户逐一指出遗漏。

相邻两轮7条变5条可分解为：3条旧岗位未复核、1条旧岗位转待核实、2条LinkedIn新增。轩宇、广东智动来自另外的同日验证任务，不混入这个7→5的算式。

主要证据为本地的 [真实任务考察](../平台改造_真实任务考察_20261009.md)、[10月8日报告](../Unity非游戏岗位汇总_20261008画像搜索.md)、[同日联网验证](../平台规则改造_联网验证_20261009.md)及各自运行账本。这些文件属于本地研究材料，不随插件发布。已有测试通过记录不等于未来修改后的测试结果。

## 2. 改造边界

- 常规预算仍按画像，默认60次，补充最多12次且包含其中；鱼泡、LinkedIn各额外最多5次。常规池继续允许所有来源，包括这两个平台。额外额度不可转移，不强制用满，不新增平台配额或结果数量下限。
- LinkedIn维持正文相对年龄未满3自然月或日期未知可保留、满3个月及以上排除的策略，并保留原文、观测日和缓存限制。可靠旧日期、明确关闭及其他硬条件仍参与判断。
- 其他平台继续采用画像原有发布/刷新窗口。不得通过放宽鱼泡日期、放行雇主不明、猜测薪资周期或擅加学历/校招排除条件改变结果。
- 搜索、打开公开页面及合法授权渠道继续使用宿主工具；遇到访问限制换公开来源核实。不得增加爬虫、验证码绕过、隐蔽接口调用或未经授权的联系招聘者行为。
- 本轮优先修复执行流程。若需要改动共用日期筛选代码，应作为独立变更验证，避免夹带到平台额度修复中。
- 保持旧账本可读、旧任务不自动加额、enrich/refresh不新增额外发现池。保留已有已完成账本与报告，纠正搜索用新任务建立来源关联，不直接篡改历史完成记录。

## 3. 推荐执行流程

1. **加载画像和相关线索。** 从当前对话、用户指定清单、最近一次同画像正式搜索及同一改造的联网验证报告中提取已知岗位URL。来源探索中的高相关候选按价值补入；不全盘扫描所有历史文件，也不混入其他画像。
2. **建立待办并分清来源。** 标明历史已纳入、本轮新发现、用户点名、已有待核实。旧事实带原观测日期，只作为复核线索；新报告的事实取得方式如实记录。
3. **开展少量宽查询及已知岗位复核。** 同时保留新发现能力。已有直达URL先正常打开，不必为了计数重新搜索公司名。
4. **每批审视增量和缺口。** 哪条路线仍产出相关候选、哪个岗位只差一项核心证据，就优先把剩余常规额度分配给相应工作。具体批次大小是执行选择，不是技能硬上限。
5. **对高价值缺口做公开反查。** 优先补雇主、职责、日期或可比薪资，再做福利、工时等非阻塞补充。
6. **主代理统一收尾。** 检查待办去向、分支未完成线索和剩余额度；分支完成或额外池耗尽不能代替全局判断。
7. **交付结果和覆盖说明。** 输出纳入、待核实、排除、去重及尚未处理线索的去向。逐项解释与上一轮的差异，保留仍未解决的问题。

## 4. 按优先级实施

### P0：先修正文档和任务交接

| 修改位置 | 具体内容 | 完成标准 |
|---|---|---|
| `skills/job-search/SKILL.md` | 开始阶段读取相关历史线索；收尾前核对已知岗位去向；明确分支配额与全任务预算的区别 | 轩宇等已知URL会被登记处理，不依赖新搜索再次偶然命中 |
| `references/retrieval.md` | 明确普通预算按增量跨平台调配；增加核心缺口公开反查；区分单路线停止和全局停止 | 有价值线索尚未处置且预算充足时，不仅凭“已做5次/8次”结束 |
| `references/worker.md` | 分支交回未完成URL、已尝试渠道、核心缺口、建议下一步和停止原因；主代理决定是否续配 | “分支额度用完”不再被解释成“该平台已经查完” |
| `references/platforms.md` | 在额外额度说明旁增加一例：额外5次用完后，仍可预留general继续查询本平台 | 域名限制、旧账本及其他来源预算规则保持原意 |
| `references/evidence.md` | 明确版本差异与影响筛选的真实冲突；补充同岗反查的证据归属规则 | 不机械把任何不同日期写为核心冲突，也不机械取最新值 |
| `references/progress.md` | 增加线索去向、覆盖缺口、全局停止理由的交付要求 | 格式检查通过与覆盖复核完成被明确区分 |

P0不需要增加查询总额、结果数量目标、强制遍历平台矩阵，也不需要新增插件依赖。

### P1：用轻量记录防止线索静默丢失

建议在现有运行数据上增加可选的线索与覆盖记录，避免另建采集系统。先定义并验证最小字段，再扩展脚本；下列字段是设计建议，当前0.2.2尚未实现。

| 记录 | 建议内容 |
|---|---|
| 线索身份 | 稳定ID、公司、岗位、直接URL；可取得时保留平台岗位ID或招聘编号 |
| 线索来源 | 原报告/运行路径、原观测日、原处置结果；本轮发现线索关联查询或访问事件 |
| 本轮处理 | 待处理、已核实并关联job_id、已合并并关联目标、暂缓并说明原因 |
| 证据缺口 | 缺哪个核心字段、已经尝试哪些来源、下一步可用渠道 |
| 收尾记录 | 停止原因、仍未处理的重要线索、各池余额及没有继续的具体理由 |

线索状态和岗位判定分开：一个线索处理完成后，岗位仍可能是待核实；没有处理过的线索不能直接宣称“岗位不符合”。归并同岗至少依据具体URL/岗位ID，或法人、招聘编号及职责地点等对应证据，不能仅凭公司同名。

实施涉及：

- `scripts/run_state.py`：扩展batch接受的新字段、原子写入、重放幂等、status摘要与complete的覆盖检查。目前batch只接受固定字段，不能直接向批次塞入新结构。
- `scripts/job_report.py`及`references/data.md`：初始化可选覆盖版本、校验数据关系，渲染简短覆盖说明。
- `references/progress.md`：说明新旧账本的兼容行为和继续任务方式。

新建且启用覆盖记录的任务，complete应拒绝“登记了重要线索却没有任何去向”的账本。预算耗尽、公开渠道受阻、线索低相关等有具体记录时，允许交付并列出限制；不能让任何一个无法核实的岗位永久阻塞任务。旧账本缺少这些新增字段时保留原流程，不强制补造历史记录。

这项检查只能发现“已登记却失去去向”，无法自动发现代理从未登记的轩宇。开始阶段的相关来源盘点，以及联网验收时独立核对旧清单，仍然必要。禁止仅填写“已全部检查”这样的布尔值代替关联记录。

### P2：统一证据裁决，按需要再调整代码

| 情况 | 推荐处理 |
|---|---|
| 已确认同一岗位、同一时间字段语义，仅页面版本值不同，所有可靠值按原规则均通过 | 保存各版本、来源和观测信息；先核实是否属于正常刷新或版本差异。能说明且不改变硬条件判断时，记录日期精确值的不确定性，不自动升级成阻塞性核心冲突 |
| 时间类型不同、日期跨筛选边界、来源对应岗位不清、出现未来日期，或可靠证据真正互相矛盾 | 保持待核实并定向补证据，不能挑一个能通过的值 |
| 搜索摘要与岗位正文日期不同 | 保留差异，比较证据归属；不以摘要自动覆盖正文，不用抓取日期代替岗位日期 |
| LinkedIn旧快照显示“1个月前” | 保留原文及观测日，说明快照无法证明实时岗位年龄；继续按现有日期例外执行，不伪造具体发布日期 |
| 岗位正文机构名与实际用人主体无法对应 | 反查原发布页或实名官方来源；没有对应证据继续待核实，不因学校/知名机构名称自动放行 |
| 页面失败或404 | 记录失败，尝试有价值的公开替代来源；单次访问失败不足以认定关闭 |

百变中级岗的问题首先来自人工将日期差异写入`merge_conflicts`。不能直接删除所有日期冲突，或改成“只要有一个时间在窗口内就通过”。若确有必要改变`job_facts.py`、`job_report.py`的通用冲突处理，需单独说明适用条件，并验证其他平台、关闭状态、薪资和真实主体冲突仍受到约束。

## 5. 公开反查的具体做法

反查适用于所有来源，优先处理方向明确、缺口具体、存在可用渠道的岗位。按缺口选择路线，不要求每条岗位走满全部步骤。

1. 提取公司全名、完整岗位名、招聘编号、城市和独特职责词。原平台正文或页面明示的发布来源优先作为下一跳。
2. 正常查看原发布平台的公开详情、企业招聘官网、官方招聘系统、高校实名公告，或有可靠同岗对应关系的其他公开平台。
3. 企业公开信息用于确认主体关系和业务，不把工商信息当成具体岗位正在招聘的证明。同名公司或相似职位不能直接合并。
4. 逐字段保留来源：哪个页面证明雇主、哪个证明职责或日期。跨来源发现数值冲突时保留冲突，不能用“面议”覆盖已披露但周期不明的工资。
5. 没有值得继续的公开线索、访问持续受阻或预算不足时，记录已尝试内容和剩余缺口，保留待核实。

已有岗位的核心信息补查按现有enrichment口径使用general，计入补充上限；寻找新的招聘机会按discovery记录。不能通过改变phase或借用额外平台额度绕过补充上限。直接打开已知URL仍记accesses；不把页面访问不扣query理解为可以无限访问。

本次两条典型线索的下一步：

- **北京大学医学部列名的Unity岗位**：正文已证明医疗VR职责、相对日期在窗口内。应围绕正文标注的智联来源、徐州地点、手术导航及培训职责反查实际招聘单位；不要先推定学校直属公司。
- **北斗天地U3D岗位**：用公司全名、U3D/Unity岗位名及已有链接线索查官网或其他公开详情。搜索摘要里的旧时间和停止申请只是线索，找到可归属的正文后再判定；禁止凭日期未知例外直接补入。

## 6. 停止条件和交付要求

允许结束一条路线的原因包括：连续低增量、该来源持续受限且缺乏公开替代渠道、该批额度用完。主代理需再检查其他路线与已知线索，才能决定全局结束。

全局收尾应回答：

- 用户点名及相关近期报告中已纳入的岗位，当前分别落在哪里？
- 还有哪些高价值核心缺口？已尝试什么，为什么暂缓？
- 额外池用尽之后，是否仍值得投入普通查询？
- 最近几批结果是否仍产生相关线索？若停止，依据是什么？
- 剩余预算与停止原因是否一致？未用满预算本身不算问题，尚有明确机会却只因分支配额结束才是问题。

报告增加简短的变化表：继续纳入、新增、转待核实、证据支持排除、合并去重、未复核。区分岗位主表和线索附录，避免用未复核候选凑合格数。全部历史岗位不必每轮重复核实，但本轮选取的相关对照范围必须明示，有价值线索被暂缓也必须可追溯。

## 7. 验证与验收

### 离线验证：规则、记账和兼容性

修改相应模块时扩展现有测试，重点放在会改变结果或造成数据丢失的行为：

| 测试方向 | 必须证明的行为 | 对应现有测试文件 |
|---|---|---|
| 额度续配 | 鱼泡/LinkedIn额外池已用满，general仍可合法查询同平台；其他平台预算不变 | `test_search_budget.py`、`test_platform_integration.py` |
| 线索续接 | 不同相关报告中的同岗正确去重；轩宇式已知线索不会无声消失；暂缓理由会显示 | `test_run_state.py`、`test_job_report.py` |
| 交付检查 | 新版覆盖记录有未处理重要线索时阻止静默完成；说明受阻或预算耗尽后允许交付 | `test_run_state.py` |
| 日期裁决 | 同语义、同边界侧的版本差异与跨边界真实冲突受到不同处理；原日期门槛保持 | `test_job_facts.py`、`test_job_report.py`、`test_linkedin_dates.py` |
| 报告与后续操作 | 原账本仍可读；新旧报告可补充/复核；enrich/refresh不获得额外发现额度 | `test_markdown_output.py`、`test_report_target.py`、`test_report_updates.py` |

只修改文档时检查规则是否自洽、路径是否正确，不编写只匹配文案的形式测试。代码改动完成后运行相关测试及现有全套回归，报告真实命令、数量和失败；147项是0.2.2历史结果，不能预填下一版验证结论。

### 真实任务验收：优先验证处理覆盖，再评估增量

使用同一画像新建纠正任务，关联本地旧账本，不解锁或重置已完成任务的计数。新一轮实际调用重新记账，不宣称使用了旧任务“剩余39次”。历史页面内容只作线索，必要时重新公开读取以核实本轮事实。

1. 盘点10月8日正式清单与10月9日联网验证中已纳入的岗位，并保留本次真实任务新增机会。至少覆盖此前暴露的百变高级、易弧、布勒、轩宇、广东智动和百变中级日期问题；名单是回归样本，不成为永久检索范围。
2. 对北大医学部列名、北斗天地等有具体缺口的候选，执行有价值的公开反查或记录无法继续的具体原因。不能只复读同一个失败URL就宣称完成反查。
3. 正常进行其他平台和官网的新岗位发现，按增量调整方向。不能为增加总数只复制旧岗位，也不能为证明额外池有效削减普通来源的工作范围。
4. 建立逐岗对照表，分清未找到、已找到但证据不足、已核实不符合，以及保留。所有纳入证据接受来源抽查。
5. 记录各池查询、发现/补充查询、页面访问、原始候选、去重候选、核心字段补齐、结果数和停止理由。记录可取得的耗时或token，不能用query数代替费用结论。

验收门槛：相关已知线索都有可追溯去向；常规来源没有受到新增的平台硬配额限制；额外池耗尽不会单独触发全局结束；证据裁决一致；真实冲突和原硬条件仍有效。公开信息受阻时可以保持待核实。

“新结果必须不少于旧结果”“查询必须达到60/70次”“每个平台至少得到若干岗位”均不作为验收标准。实时网页可能变化，岗位数量自然波动。固定事实回放、历史清单处理覆盖、联网新发现能力是三个不同维度，结论分别报告；任何一项未验证，不声称整体召回或工作流程已经证明无害。

## 8. 实施与发布顺序

1. 先完成P0指令修复和P1最小覆盖记录，确认P2是否需要代码变更；保持改动集中、可回退。
2. 本地验证后备份并同步到实际Codex插件安装目录，核对同步文件与工作区版本，使用实际安装路径运行必要检查。
3. 执行上述真实纠正任务，形成新岗位报告、逐岗差异和改造验收记录。若仍出现线索丢失、无理由收尾或其他平台规则被放宽，先修复并复验。
4. 达到验收标准后，再按此前授权安排版本提交、推送及Codex重新安装，核对安装版本和文件一致性。个人画像、求职清单、原始账本继续留在本地忽略目录；仓库测试使用最小脱敏样例。
