# 以信息增量分配查询

用于新岗位发现或专项补充。以下是选下一次查询的参考，不是必须完成的路线或配额。

## 找岗位

根据画像选少量主要业务方向与常见叫法，随着结果调整。例如 Unity 非游戏可涉及数字孪生、工业仿真、虚拟实训、展陈交互；Unity/U3D/Unity3D 是检索变体，不是新增硬条件。一次查询通常围绕一个清晰方向；不要把所有技术、地点和福利词堆在同一查询。

不同网站反复出现同批职位时，优先换业务方向、岗位叫法或来源类型。官网、高校实名公告、招聘平台具有不同覆盖，按可用性选择；不要求固定数量或遍历全部组合。不要在发现阶段机械使用 `-游戏` 排除词，以免漏掉“游戏引擎经验”等非游戏岗位。

日志可简记 direction（本次方向）、new_jobs（去重后新增候选数）、new_fields（新增且有来源的字段数）；不能把公司参考福利计为本岗已确认福利。不必为每条搜索建立完整矩阵。下一批先看已有结果和明显缺口；缺口本身不会阻止收尾。

连续查询增量很低时，若仍有一个重要方向未触及，可用剩余额度换方向试一次；若无有价值的线索就收尾。不要为满足来源数量、覆盖率或预定岗位条数耗完预算。

## 补资料

先从已有相关页面提取本次范围内的全部可用信息；只对剩余缺口新增查询。按具体缺口选来源：

| 缺口 | 优先线索 |
|---|---|
| 本岗福利、每日起止、每周天数 | 原岗位正文；明确适用于该岗位的公司制度 |
| 公司统一福利 | 对应公司官方招聘介绍，标明公司口径 |
| 社保人数 | 准确法人名称与年报年份/参保信息，不与“福利、双休”混查 |
| 岗位讨论 | 公司、岗位方向和具体主题；保留时间和个人反馈属性 |

同次任务中，同一法人且适用范围一致的资料可复用；不同子公司、年份、城市制度或其他工种不可直接套用。来源受阻、未搜索、已查未披露分别保留，不能据搜索无增量断言网上没有资料。

## 成本与恢复

query 数是预算口径；页面访问另记 accesses，不能把“查询不增加、无限打开页面”视为同成本优化。页面必要时只保留相关片段和短事实，不保存整页。

每批取得结果后及时写入日志与事实，再开展下一批。记录方法见 [progress.md](progress.md)，可直接编辑原账本，也可用简短命令追加；不需要新增审批。工具调用与本地落盘不是同一事务，中断时仍需结合工具记录补记已执行调用，不能把未落盘当作未执行。

评估改进应区分：新增有效岗位、核心证据补齐、指定字段补齐、query 数、页面访问数和可取得的 token 用量。不要求线上结果每次一致；固定材料回放用于检查同证据处理效果。
